# 검증

구름이는 실차 없이 만들었습니다. 그래서 판단 규칙은 단위 테스트로, 차량 신호와 성능은 에뮬레이터로 확인했습니다. 실차에서만 알 수 있는 것은 끝에 따로 적었습니다.

## 단위 테스트

단위 테스트는 603개이고 모두 통과합니다. 전부 Android 없이 JVM에서 돌아갑니다. 판단 엔진은 시각을 입력으로 받습니다. 그래서 한 시간 주행이나 10년치 기록도 기다리지 않고 시험합니다.

| 묶음 | 수 | 다루는 것 |
|---|---|---|
| 운전 판단 | 66 | 트립(출발~도착 한 번)의 시작과 끝, 급제동, 살살 멈추기, 깜빡이, 쉬어 가기, 보상 한도, 시계 이동 |
| 함께 탄 사람 | 94 | 자리별 안전벨트, 내렸다 다시 타기, 탈 아기 고르기, 부른 이름 알아듣기 |
| 성장과 수집 | 187 | 깃털과 병, 선물, 주워 온 것, 앨범, 운전 버릇, 정비 수첩, 차종, 강가 |
| 시간과 회상 | 84 | 함께한 날, 기념일, 그림책, 창밖 장면 |
| 말과 소리 | 92 | 도착 일기, 홈 말풍선, 말투 점검, 소리 내어 읽는 숫자, 말 미루기, 달리는 동안의 소리 |
| 기록 | 28 | 기록 파일 저장과 다시 읽기, 잘린 줄, 옛 형식, 가족 파일, 한 주 동안 가족이 타고 내리는 흐름 |
| 화면과 엽서 | 52 | 소품과 사진 자리, 글자 크기와 대비, 누를 곳 크기, 뜨거울 때 움직임, 엽서와 QR |

- 신호 순서를 무작위로 섞는 시험도 있습니다. 무작위 순서 300가지를 500걸음씩 넣습니다. 트립이 겹치거나, 달리는 중에 안전벨트를 부탁하는 일이 없는지 봅니다.
- 버그를 고친 곳을 하나씩 되돌려 보는 시험도 했습니다. 11월 2일 자동차 상황 시험에서 고친 코드 20곳 가운데 19곳을 테스트가 잡았고, 나머지 1곳은 동작이 같은 최적화입니다. 그 뒤에 고친 곳은 이 시험을 하지 않았습니다.
- 서비스, 음성 재생, 화면 그리기는 Android에 기대므로 단위 테스트가 없습니다. 규칙만 떼어 고정하고, 나머지는 에뮬레이터에서 확인합니다.
- 돌리는 명령은 [개발 환경](development.md)에 있습니다.

## 에뮬레이터에서 확인한 것

Pleos Connect 에뮬레이터 v2.1(Android 14)에서 확인했습니다. Virtual Console로 차량 상태를 바꿉니다. 앱이 받은 신호와 이벤트는 검증 빌드(debug)의 로그로 봅니다.

| 신호 | 에뮬레이터에서 | 앱이 쓰는 곳 |
|---|---|---|
| 기어 | P, R, N, D를 받음 | 트립의 시작과 끝 |
| 속도 | 0.1~0.2초 간격으로 받음 | 급제동, 살살 멈추기, 달린 거리 |
| 브레이크 | 밟았는지만 받음 | 급제동 조건 |
| 깜빡이, 핸들 각도 | 받음 | 깜빡이를 먼저 켰는지 |
| 경고등 | 켜고 끄기를 받음 | 정비 수첩, 출발 때 안전벨트, 안개와 눈 장면 |
| 자리별 안전벨트 | 처음 값만 받음 | 아기 정령 깨우기. 시험 입력으로 확인 |
| 누적 주행거리 | 넣은 값만 받고 달려도 그대로 | 정비 주기 |

- 속도는 Vehicle SDK에 없어서 Android Automotive 표준 차량 속성으로 받습니다.
- 에뮬레이터는 자리별 안전벨트가 바뀌는 신호를 주지 않습니다. 아기 정령이 깨어나는 장면은 검증 빌드의 시험 입력으로만 확인했고, 제출 APK로는 에뮬레이터에서 볼 수 없습니다.
- 무엇을 잘한 일로 세는지는 [차량 신호와 판단 기준](signals.md)에 있습니다.

`scripts/vc-trip-15s.js`는 Virtual Console에서 약 12초짜리 트립을 돌립니다. 살살 멈추기는 감속이 2.5 m/s²를 넘지 않게 멈춘 경우입니다. 급제동은 브레이크를 밟은 채 3.5 m/s² 이상으로 줄인 경우입니다.

| 시각 | Virtual Console | 앱이 남기는 이벤트 |
|---|---|---|
| 0초 | D로 바꾸고 가속 | `TripStarted` |
| 1.8초 | 약 25 km/h로 정속 | 없음. 정속 뒤에 멈춰야 살살 멈추기로 셈 |
| 3.3초 | 브레이크 9%로 멈춤 | `SmoothStop`. 최대 감속 약 2.1 m/s² |
| 10.1초 | 다시 달리다 브레이크 60% | `HardBrake`. 판정 때 감속 약 5.7 m/s² |
| 11.8초 | P로 바꿈 | 3초 뒤 `TripEnded`와 도착 일기 |

플랫폼 동작도 함께 확인했습니다.

- 다른 앱이 앞에 있어도 서비스가 신호를 받습니다. 내비가 앞에 있을 때도 Virtual Console 조작이 그대로 들어왔습니다.
- D로 바꾸면 플랫폼이 앱 화면을 "주행 중에는 사용할 수 없습니다"로 가립니다. P에서 다시 보이고, 서비스는 그동안에도 돌아갑니다.
- 다른 앱이 앞에 있으면 플랫폼이 도착 카드를 띄우지 못하게 막습니다. 이때는 카드 대신 알림으로 남깁니다.
- 앱을 한 번 연 뒤로는 에뮬레이터를 켜기만 해도 서비스가 뜹니다. 차량 연결은 메인 스레드 밖에서 해서 부팅 때 ANR이 나지 않습니다.

## 자동차 상황 시험

폰 앱은 겪지 않는 상황도 에뮬레이터 명령으로 만들어 시험합니다. 11월 2일 빌드로 돌린 결과 9개 상황 가운데 7개가 합격입니다. 사용자 전환은 아직 판정 전이고, 오래 켜 두기는 30분만 돌렸습니다. 그 뒤 빌드로는 다시 돌리지 않았습니다. 상황마다 지켜야 할 기준은 이렇습니다.

- 시동 끔과 복귀, 최대 절전: 깨어나면 서비스가 다시 뜨고 기록이 빠지지 않아야 합니다.
- 쓰는 도중 강제 종료와 전원 차단: 다 쓴 줄은 하나도 잃지 않아야 합니다. 기록 파일은 한 줄마다 fsync로 디스크에 씁니다. 에뮬레이터가 실제로 꺼졌을 때도 잃은 줄이 없었습니다. fsync 없이 쓴 2,000줄은 대조 시험에서 모두 사라졌습니다.
- 느린 저장: 저장 앞에 3초까지 지연을 넣어도 메인 스레드가 멈추지 않아야 합니다.
- 시계 이동: 시계를 앞뒤로 옮겨도 트립 길이가 음수가 되면 안 됩니다. 이 시험에서 음수 트립, 끝나지 않는 트립, 다시 읽을 때 죽는 문제를 찾아 고쳤습니다. 지금은 단위 테스트 19개가 막습니다.
- 열과 메모리: 플랫폼이 뜨겁다고 알리면 움직임을 3배 늦춥니다. 메모리가 모자라다는 신호를 손으로 보내면 쥐고 있던 그림을 놓습니다. Android 14가 실제로 이 신호를 보내는 때는 확인하지 못했습니다.

## 성능

목표는 대부분 [Pleos 앱 심사 기준](https://document.pleos.ai/docs/pleos-only/distribute/app-review-guide/review-functionality-performance-stability)의 70%로 잡았습니다. 30% 여유는 표준이 아니라 직접 정한 값입니다. 실차 환산은 대상 차 가운데 가장 약한 아반떼 기본형에 맞춥니다. 그 칩의 공개 성능값이 없어 비슷한 급(SA8155P)의 값을 빌려 썼습니다.

에뮬레이터 값은 두 가지로 나눠 읽습니다.

- 앱이 요청하는 프레임 수, 메모리, 저장량, 설치 파일 크기는 코드가 정합니다. 실차에서도 거의 같아서 예산을 넘으면 불합격입니다. 다만 메모리는 에뮬레이터가 그래픽 메모리를 앱 몫으로 세지 않아, 실차에서는 그만큼 더해집니다.
- CPU와 시간은 에뮬레이터를 돌린 PC의 값입니다. 실차 값은 단일 코어 성능 비율로 바꾼 추정이라 경고로만 씁니다. 환산에는 GPU 드라이버 비용처럼 출처 없이 잡은 가정이 들어 있어 폭이 넓습니다. 정차 중 CPU의 계획값은 18%이고 범위는 13~32%입니다.

시간 값은 측정 빌드로 잽니다. 제출 빌드 코드에 검증용 계측을 더한 빌드입니다. 검증 빌드는 인터프리터로 돌아서 시간이 부풀므로 쓰지 않습니다.

장면마다 부팅을 여러 번 되풀이해 잽니다. 부팅 단위로 복원추출해 95% 신뢰구간을 내고, 구간 상한이 목표 아래면 통과입니다. 부팅이 두세 번뿐인 비교는 판정하지 않습니다. 앱을 켠 뒤 60초는 버리고, 다른 에뮬레이터와 화면 미러링은 끈 채로 잽니다.

| 항목 | Pleos 기준 | 목표 | 지금 값 |
|---|---|---|---|
| 정차 중 CPU | 25% 이하 | 17.5% | 낮 집 화면에서 실차 환산 약 15~17%(에뮬레이터 값 22~26%) |
| 주행 중 CPU | 5% 미만 | 3.5% | 기어 D로 서 있을 때 실차 환산 약 1.1%. 달릴 때 값은 아래에 |
| 메모리 | 400 MB 이하 | PSS 280 MB | PSS 77~93 MiB(켠 뒤 2~3분) |
| 실행 | 10초 이내 | 5초 | 첫 프레임 0.7~1.2초(에뮬레이터, 흐린 미리보기 그림까지. 최종 빌드 1.19초) |
| 설치 파일 | 600 MB 미만 | 420 MB | 제출 APK 47 MB |

- 표의 값은 따로 적지 않으면 11월 8~9일에 측정 빌드로 잰 것입니다. 11월 12일에 최종 코드로 첫 프레임, 터치, 도착 화면, 달리는 중을 다시 쟀습니다. 정차 중 CPU는 다시 재지 않았지만, 그 뒤 바뀐 코드(처음 켠 날의 순서, 성장 기록 쪽 배치)는 집 화면의 그림을 그리는 코드가 아닙니다.
- 주행 중 CPU 1.1%는 기어만 D에 두고 서 있는 장면입니다. 11월 12일에 속도를 넣어 달린 구간(D 구간만)을 다시 재니 실차 환산 약 0.8~0.9%였고, 홈은 한 프레임도 그리지 않았습니다. 다만 트립 다섯 번 중 두 번 에뮬레이터가 꺼져 세 번만 남아 표본이 적습니다.
- 정차 중 CPU는 낮 집 화면 값입니다. 밤 집 화면은 11월 9일에 15초짜리로 한 번 재서 환산 18%쯤이었는데 표본이 부족합니다. 11월 2일 빌드로 부팅 세 번에 걸쳐 잰 값은 20~22%로 목표 17.5%를 넘었습니다. 성장 기록 쪽은 11월 2일 빌드에서 19%였습니다.
- 첫 프레임은 흐린 미리보기 그림이 뜰 때까지입니다. 11월 8일에는 0.74초, 11월 12일 최종 빌드는 1.19초였습니다. 같은 날 번갈아 잰 11월 9일 빌드는 1.07초였고, 네 묶음 모두 최종 빌드가 0.1초쯤 길었습니다(원인은 아직 모름). 11월 8일과의 차이는 빌드와 잰 날이 함께 달라 까닭을 가르지 못합니다. 집 장면이 다 그려지기까지는 11월 2일 빌드에서 4.4~6.0초였고, 그 뒤로 다시 재지 않았습니다.
- 메모리는 켠 뒤 2~3분의 값입니다. 30분 켜 둔 시험(11월 2일 빌드)에서는 가장 클 때 110.8 MiB였습니다.
- 달리는 동안 홈은 한 프레임도 그리지 않습니다. 정차 중 홈은 숨만 쉴 때 초당 9장, 몸짓 때 15장을 요청하고, 잰 평균은 약 10장입니다. 책 화면은 초당 15장 안입니다.
- 혼잡 시험을 뺀 모든 측정 구간에서 앱의 크래시, ANR, 프로세스 사망은 0입니다. 에뮬레이터가 꺼지거나 측정이 끊겨 건너뛴 부팅은 세지 않았습니다.
- 정차 중 CPU는 목표에 가까워 아직 통과로 보지 않습니다. 같은 빌드도 재는 시각에 따라 실차 환산 16%와 22%로 갈린 적이 있습니다.
- 낮 집 화면에서 메인 스레드가 한 번에 가장 오래 막힌 시간은 38~49 ms로, 에뮬레이터 경고선 39 ms 근처이거나 조금 넘습니다. 화면을 계속 누를 때와 도착 카드에서는 71~80 ms로 경고선을 넘습니다. 이 선은 실차 목표 0.175초를 느린 코어 비율 3.2배와 고온 여유 1.4배로 나눈 값입니다. 막힌 시간의 대부분은 앱이 하는 일이 아니라 그래픽 파이프라인 대기로 봅니다.
- Pleos 기준 400 MB가 PSS인지 RSS인지는 밝혀져 있지 않습니다. RSS로 봐도 장면별 평균이 192~222 MiB입니다. 이 값에는 측정 때 뒤에 띄운 검증 콘솔 몫 약 5 MiB가 들어 있습니다.
- 혼잡 시험도 했습니다. PC가 에뮬레이터에 주는 CPU를 4개로 묶으면 앱을 켤 때 ANR이 날 수 있습니다. 스택이 에뮬레이터 그래픽 파이프라인 대기라서 환경 한계로 봅니다. 다만 실차의 느린 코어에서도 생길 수 있어 실기기에서 다시 볼 항목입니다. 크래시와 프로세스 사망은 없었습니다.

## 실차와 에뮬레이터가 다른 점

- 에뮬레이터는 GPU 대신 PC의 CPU로 그립니다. 집 화면에서 앱 CPU의 90~92%가 커널 시간이고(11월 8~9일 값, 11월 2일에는 86~91%), 대부분 그래픽 파이프라인을 기다리는 시간입니다. 실차에서는 이 몫이 GPU 드라이버 비용으로 바뀝니다.
- 실차 코어는 개발 PC보다 느립니다. 메인 스레드 시간은 단일 코어 성능 비율 2.5~3.2배로 늘려 봅니다. 개발 PC와 대상 칩의 단일 스레드 벤치마크 점수 비율이고, 이 앱을 실차에서 잰 값이 아닙니다.
- Virtual Console의 제동은 약 1.2 g로 실제 차보다 셉니다. 타이어 공기압 값은 에뮬레이터에 없어서 경고등으로 대신합니다.
- 에뮬레이터가 주행을 시작하고 15~25초쯤에 꺼진 적이 있습니다. 시연 트립을 15초 안으로 끊은 이유입니다. 그 뒤에도 서 있을 때와 화면을 녹화할 때 멈추거나 꺼진 일이 여러 번 있었습니다(11월 3일~10일). 11월 12일에도 속도를 넣어 달리는 측정 다섯 번 가운데 두 번 꺼졌습니다. 앱 탓인지는 가리지 못했습니다.
- 콜드 부팅 직후 1분쯤은 내비 앱이 저절로 켜지는 등으로 신호가 늦게 들어옵니다. 시험은 그 뒤에 합니다.
- 에뮬레이터의 RAM 4 GB는 차량 값이 아닙니다. 대상 차의 RAM과 저장장치는 공식값이 없습니다.

## 아직 확인하지 못한 것

- 실차에서 잰 값이 없습니다. 실차 성능은 모두 추정이고, 실제 ARM 칩을 쓴 기기로 재는 단계도 아직입니다.
- 속도(`CAR_SPEED`)와 경고등(`PRIVATE_CAR_SAFETY`) 권한을 심사에서 받을 수 있는지 모릅니다. 상주 서비스와 부팅 뒤 자동 시작이 허용되는지도 모릅니다. 속도가 막히면 급제동, 살살 멈추기, 깜빡이, 거리 판단이 멈춥니다. 경고등이 막히면 경고등으로 아는 몸 상태, 출발 때 안전벨트, 안개와 눈 장면이 꺼집니다.
- 자리별 안전벨트와 뒷문, 핸들 각도 단위는 실차 신호로 확인하지 못했습니다.
- 차 안전벨트를 쓰지 않고 고정하는 카시트(ISOFIX)는 알아보지 못합니다. 그 자리의 아기 정령은 깨어나지 않습니다.
- 달리는 동안의 소리(출발 차임, 깃털 소리)가 실차의 소리 정책에서 그대로 나는지는 모릅니다. 에뮬레이터에서만 확인했습니다.
- 차량 음성 비서 Gleo와는 모의로 주고받는 데까지만 확인했습니다. 실제 말로 묻고 답하는 흐름은 아직입니다.
- 터치 반응 0.25초 규칙은 실물로 재지 못했습니다. 에뮬레이터에서 터치부터 다음 프레임까지는 38~43 ms로(최종 빌드 42.8 ms, 두 번 켜서 잰 값이라 표본이 적음), 경고선 39 ms에 걸쳐 있거나 조금 넘습니다. 앱을 켠 뒤 집 장면이 다 차려지기까지의 시간도 실차 기준으로는 모릅니다.
- 절전 시뮬레이션은 프로세스를 얼리지 않아 실제 절전과 다릅니다. 저온과 저전압은 재현하지 않았고, 부하가 클 때 기록이 빠지는지도 재지 못했습니다.
